# Архитектура безопасности: Аутентификация и Авторизация в TeachLab

## 1. Терминология

* **Аутентификация:** Проверка подлинности пользователя (проверка соответствия email и введенного пароля).
* **Авторизация:** Разграничение прав доступа на основе ролевой модели (Role-Based Access Control — RBAC)
  * `tutor` (преподаватель)
  * `student` (ученик).

## 2. Безопасность хранения паролей: Хэширование и Соль (Bcrypt)

Пароли пользователей **никогда не хранятся в открытом виде** в базе данных. Для защиты используется алгоритм **bcrypt**:

1. **Хэширование:** Преобразование пароля в необратимую криптографическую строку фиксированной длины. Даже в случае утечки базы данных восстановить исходный пароль невозможно.
2. **Криптографическая соль (Salt):** К каждому паролю перед хэшированием добавляется случайная уникальная строка (соль). Это защищает базу от взлома по заранее вычисленным радужным таблицам (Rainbow Tables), так как два одинаковых пароля `12345` у разных пользователей дадут абсолютно разные хэши в базе данных.

## 3. Выбор технологии JWT (JSON Web Token)

Для поддержания сессии пользователя выбран стандарт **JWT (RFC 7519)**.

### Почему JWT, а не классические сессии в базе (Session Cookies)?

1. **Архитектура без состояния (Stateless):**  
   Серверу не нужно хранить сессию каждого пользователя в оперативной памяти или базе данных. Вся необходимая информация (ID пользователя, email, роль `tutor`/`student`) зашита в сам токен и подписана секретным ключом сервера (`SECRET_KEY`).
2. **Идеально для SPA (React + FastAPI):**  
   Фронтенд на React получает токен при входе и отправляет его в заголовке `Authorization: Bearer <token>` к каждому запросу. Это стандарт разработки современных API.
3. **Производительность:**  
   Сервер проверяет подлинность токена математически (через криптографическую подпись), не делая лишних тяжелых запросов в базу данных при каждом клике пользователя.

### Схема работы:
1. Клиент отправляет `POST /api/v1/auth/login` с логином и паролем.
2. Сервер проверяет хэш пароля с солью в PostgreSQL.
3. При успехе сервер генерирует строку **JWT Access Token** со сроком жизни (например, 24 часа) и отдает клиенту.
4. Клиент сохраняет токен и прикрепляет его к запросам на создание тестов и просмотр классов.
